## Coverage

I reviewed `git diff HEAD~3`, `REPORT.md`’s fix-loop-2 claims, the revised workflows and scripts, the generated inventories, the pinned hexx checkout, the origami engine source form, plan §§4.4 and 9, and D-132’s release instructions. Decision C withdraws the former allowlist finding for `docs/RELEASING.md`.

`api_parity.py --check`, `--extensions --check`, `gas_tables.py --check`, and `deviations.py --check` passed. The 701-item embedded inventory exactly matches a fresh read-only parse of `sources/hexx`; all 66 canonical L-M1 keys were found. My mocked parser and bench probes produced the scenarios above. The full unit command ran **70 tests: 34 passed, 36 errored while trying to create fixture directories**; `scripts/tests/tmp` is also read-only here. `scripts/check.sh` stopped at Scarb’s `failed to open lockfile: Read-only file system`. `gh pr checks 18` could not reach GitHub, so the implementer’s green-CI and package claims remain independently unverified. No files were changed; `git status --short` is clean.

CI has pull-request and `main` triggers, fixed action SHAs, `contents: read`, and no reference to a repository or registry secret. Its pull-request package job uploads the archive; the manual release check uploads its manifest and archive listing. Checkout necessarily uses GitHub’s limited token, but neither workflow receives `SCARB_REGISTRY_AUTH_TOKEN`. The release-check version mapping, generated-trait gap, and decision-B parser failures prevent this lot from serving as the complete gate for M1-T1’s planned candidate.
