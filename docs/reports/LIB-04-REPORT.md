**Can the `#[available_gas]` form and a snapshot form be derived from one another (plan §4.2)?**
Yes, and this task's tooling is built on that: `gas/*.snap` is the single source of truth
(written by `scripts/bench.py snapshot` from one `snforge test --detailed-resources` run per
package); the `#[available_gas(l2_gas: N)]` budget is a deterministic function of the snapshot's
`measured` column (`N = ceil(1.05 × measured)`), and `docs/GAS.md` is a deterministic rendering
of the same snapshot (`scripts/gas_tables.py`, no snforge run). One measurement, two derived
views. This differs from the house `glam-cairo` form (paired `X__base`/`X__op` benches, whose
snapshot *is* the two-run delta, not a companion of a per-test attribute) only because this
package's tests are not written in `base`/`op` pairs; nothing here needed the paired form, so it
was not adopted.

## Deviations

From the brief, each with its reason:

1. **`tools/refgen`'s golden file is not under `crates/hexx/tests/`.** Confirmed empirically:
   Scarb bundles every `.cairo` file directly under a package's `tests/` directory into one
   `<package>_integrationtest` compilation unit even with no `tests/lib.cairo` present. The
   first attempt (`crates/hexx/tests/golden_hex.cairo`, calling the not-yet-existing
   `hexx::hex::Hex`) broke `scarb build -p hexx` / `snforge test -p hexx` immediately
   (`E0006`/`E0002`). There is no "declared but not compiled" state for a loose file there. The
   generator now writes to `tools/refgen/generated/golden_hex.cairo`; `tools/refgen/README.md`
   records the finding and says M1-T2 moves the file in once the mirror exists.
2. **`scripts/api_parity.py` does not walk `layout`, `storage` and `mesh`** (plan §4.4 "Modules
   excluded as a whole", ~148 items). These are whole-module exclusions with one shared reason
   each (`f32` world/screen space; on-chain storage and boards replace the generic containers;
   rendering); building the same per-item fidelity the kept modules have for them was not worth
   the time this task had, against modules with no ambiguity in their status. Recorded as a
   scope limit in `docs/API_PARITY.md`'s own header and here, per COMMON.md's evidence rule,
   rather than silently omitted. `docs/API_PARITY.md`'s percentage is computed over the modules
   the parser does walk (`hex`, `direction`, `conversions`, `bounds`, `shapes`, `algorithms`,
   `grid`), consistent with what it actually inventories.
3. **Two small known gaps in the embedded inventory, found while cross-checking plan §4.4's
   "Counts" against the parser's own totals** (used as a sanity check, not copied uncritically):
   the Rust side does not recognize `Deref` as an impl trait (so `impl Deref for HexOrientation`,
   excluded either way, is silently absent rather than an explicit `dropped` row), and it does
   not scan `#[derive(Default)]`/`#[default]` variant attributes on an enum (so `HexOrientation`'s
   derived `Default` is similarly absent). Both concern already-excluded or already-ported items
   (`HexOrientation`'s status is unaffected either way); `docs/API_PARITY.md`'s `HexOrientation`
   row is 8 items where the plan's prose implies about 10. `direction::mod.rs`'s nested `pub mod
   angles` (4 `f32` constants) is not walked either, for the same reason as finding 2 — one more
   module-level exclusion, at negligible scale. Every other owner's total matched plan §4.4's
   "Counts" exactly or within one item once two real parser bugs were found and fixed while
   building this table (see below) — I take that agreement as the stronger signal than these
   three residual gaps, which I chose to record rather than keep chasing.
   - **Two bugs found and fixed in the same pass** (worth recording since they show the "Counts"
     cross-check did its job): the impl-target filter first used the global owner set instead of
     each file's own locally declared types, which silently dropped every `Default` impl of
     `shapes.rs` (its six shapes' `Default` never appeared at all, not even as `missing`); and
     multiple structs sharing one owner in the same file (`shapes.rs`) collapsed same-named
     methods/fields (`new`, `coords`, `left`, …) into one item on the (owner, kind, name) dedup.
     Both fixed (`scan_impls`'s `allowed_targets` parameter; `scan_multi_struct_file`'s
     `Type.field` / `Type.method` scoping) and re-verified against plan §4.4: `shapes` now reads
     43 items, the exact count the plan's "Counts" section states (15 functions + 6 structs with
     16 public fields + 6 `Default` impls).
4. **Milestone tagging in `docs/API_PARITY.md` is best-effort, not exhaustively transcribed from
   plan §4.4.** Every item of the explicit L-M1 set (`Hex`'s core fields/constructor/distance,
   `line_to`, the offset conversions, `EdgeDirection`'s core, `HexOrientation`) is tagged `L-M1`
   by name; every other kept-module item defaults to `L-M2`, `algorithms` items to `L-M3`. This
   is accurate for what `--check-release` and its unit tests need to demonstrate (AC-3), and is
   marked "best-effort" in the generated file itself; a milestone-perfect transcription of all
   ~300 items was not attempted in the time this task had.
5. **`scripts/bytecode_size.py`'s `attribution` subcommand (marginal cost per call site) is
   dropped**, not adapted. It needs a heavy library item to probe; nothing in `hexx` is ported
   yet, so there is no fixture for it to run against before LIB-05. `table`/`snapshot`/`check`
   (what the brief's *Interfaces* and every acceptance criterion actually need) are kept.

### Scope item 7: `origami_hexmap` 1.8.0's `snforge_std` defect

The plan (§2.1) states that `origami_hexmap` 1.8.0's *source* manifest correctly declares
`snforge_std` under `[dev-dependencies]`, yet the *published* package is "resolved by its
consumers as depending on `snforge_std >=0.61.0, <0.62.0`" (`grimworld:docs/needs/hexmap.md`
§ "N-9 in detail", failure 1) — a regular dependency, from the consumer's point of view. LIB-04
was asked to find where this happens (the packaging step, the registry's index, or the Scarb
version that published 1.8.0) without publishing anything, and to write down the answer.

**What this task found, all without publishing:**

1. **`scarb package -p hexx`, on Scarb 2.19.4, correctly normalizes `snforge_std` as a
   dev-dependency** in the packaged `Scarb.toml` (real output above; `[dev-dependencies.snforge_std]
   version = "^0.61.0"`, and an empty `[dependencies]` table — nothing leaked in). **The
   packaging step, on the current toolchain, is not the cause** for a package shaped like
   `crates/hexx`.
2. **`scarb metadata` on `crates/takeover_tests` (which depends on the *published*
   `origami_hexmap = "1.8.0"` from the registry, resolved for real from scarbs.xyz — no
   publishing involved, only consuming an existing package) shows the dependency graph correctly
   separates the two**: `origami_hexmap`'s own package entry lists `snforge_std` with
   `"kind": "dev"`; the **`lib` compilation unit** of `takeover_tests` (its regular, non-test
   build) resolves to exactly `core`, `origami_hexmap`, `takeover_tests` — **`snforge_std` is not
   part of it**. It only appears in the **`test`** compilation unit, and there because
   `takeover_tests` itself declares `snforge_std` as its own dev-dependency (needed for its own
   test), not because it was pulled in through `origami_hexmap`. **On the current registry state
   and Scarb 2.19.4, a plain `scarb build` of a consumer of the published `origami_hexmap` 1.8.0
   does not resolve `snforge_std` into its build graph.**
3. Fetching `origami_hexmap`'s page on scarbs.xyz itself (`https://scarbs.xyz/packages/origami_hexmap`)
   shows **no dependency information at all**, dev or regular — the registry's own package page
   does not surface the distinction visually.

**Reading of the evidence**: the packaging step (1) and Scarb's own dependency resolution (2), on
the toolchain and registry state available to this task today, both correctly treat
`snforge_std` as dev-only for a consumer's regular build. This does not reproduce the failure the
plan cites. Two explanations remain, neither closable without either an older Scarb toolchain
(to package/test against, which this task's machine does not carry — the profile refuses
installing one) or the game's own repository (to see the exact failing command and Scarb version
it ran): (a) the failure was observed under a different Scarb version than 2.19.4 — 1.8.0 could
have been *published* by an older Scarb whose normalization step behaved differently, which
`scarb metadata`'s consumer-side re-resolution today cannot see (the packaged manifest on the
registry is what it is, immutable per version); or (b) the failure is not about the *build*
graph at all but about **version resolution**: if the game's own workspace pins `snforge_std` at
a version outside `origami_hexmap`'s `^0.61.0` *dev*-requirement, Scarb may still need to
unify that requirement during resolution (even though it prunes it from the final non-test build
graph), which could surface as a resolution conflict rather than a leak — a different failure
mode than "resolved as depending on", but consistent with the symptom being observed at
`snforge_std` version-pinning time rather than at plain-build time. **Recorded, not closed**: the
project manager or a task with access to the game's repository and its exact failing command is
better placed to confirm which of (a) or (b) matches what was actually observed.

### A ReDoS found and fixed while rewriting the parser for finding 4

The first version of the `find`-generic-then-brace regex (`(?:<[^{;(]*>)?\s*\{`, used to skip a
struct's generic parameters before its brace) hung for minutes on `storage/rect.rs` once
`split_own_and_children` started blanking out large inline `#[cfg(test)] mod ... { ... }` regions
to spaces (needed for finding 4's own fix): a negated character class with no matching literal
for thousands of characters, tried from every position `finditer` considers, is the textbook
catastrophic-backtracking shape. Replaced by `find_declaration_body`, a manual, non-backtracking
character scan (bounded generic-depth tracking, no regex) — see its docstring in
`scripts/api_parity.py` for the full account, kept there because the next person changing this
parser needs to know why a hand-written scan replaces what looks like a simpler regex.
